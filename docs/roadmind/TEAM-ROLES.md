## 一、口径说明（先对齐这个，再往下看）

> ⚠️ **本仓库统一采用一套 P 编号映射**，三个候选方向共用。见 [`../../README.md`](../../README.md)，BoostForge 与 PathPilot 同此口径。

| 编号 | 角色 |
|---|---|
| **P1** | 产品 + 业务 |
| **P2** | 后端 / 架构 |
| **P3** | 算法 / 核心智能 |
| **P4** | 前端 / 全栈 |

**为什么必须统一**：早先 RoadMind 的两份文档用过两套编号 —— `EXECUTION-PLAN.md` 第七节曾写「P1 调度 / P2 视觉 / P3 前端 / P4 业务」，而被替换掉的那份接入方案文档写的是「P1 队长 / P2 后端 / P3 算法 / P4 业务」。**同一个「P3」，一份文档里是前端、另一份里是算法。**（两处均已按本文件统一。）

统一之后的好处是：**换方向不换人**。最终选 BoostForge 还是 RoadMind，四个人的角色含义始终一致，不需要重排座次。

## 二、角色分工总表

| 角色 | 一句话定位 | 负责的 Agent / 模块 | 核心交付物 |
|---|---|---|---|
| **P1 · 队长 / 产品 + 交通业务** | 定义「什么算一条要件」 | 法条知识底座、**文书切分标准**、数据源落地 | 要件库 v1、切分标准、真值抽检报告、设计报告、答辩 PPT |
| **P2 · 后端 / 架构** | 让 4 个 Agent 能互相说话，也让文书进得来 | 编排层、A1/A2 工程实现、**文书数据管道**、评测流水线 | 三段切分管线、消息 Schema、工具层、护栏校验器、闭环脚本 |
| **P3 · 算法 / 核心智能** | 全案唯一「会改主意」的地方 | **★A4 复盘**、**A3 对抗质证** | 要件库演化策略、对抗策略、三组对照实验、评测报告 |
| **P4 · 前端 / 全栈** | 让「会改主意」在屏幕上被看见 | 交互层（不写 Agent，消费全部输出） | 研判工作台、**前后对比视图**、**思考链可视化**、上架材料 |

> ℹ️ **与上一版的差异一目了然**：P2 的大头从「SUMO 接入」变成「**文书数据管道**」；P4 的大屏与出行页删除，换成**前后对比视图**；P1 新增「**切分标准**」这一项业务判断。

## 三、逐人详表

### P1 · 队长 / 产品 + 交通业务

| 项 | 内容 |
|---|---|
| **对应 Agent** | 为 **A2 要件对照 / A4 复盘** 提供知识底座（定标准，不写 Agent 代码） |
| **交付物** | ① **数据源落地**：合法拿到 ≥50 份交通事故裁判文书（验证清单第 2 项）② **★ 文书切分标准** —— 什么算一条要件、哪段是输入哪段是真值 ③ **要件库 v1**（≥30 条高频条款，含**要件拆解**）④ **真值抽检报告**（30 条人工校验）⑤ 方案设计报告 ⑥ 答辩 PPT + 主讲 + 彩排 |
| **上游依赖** | 无（本方向的知识底座是**根节点**，不等人） |
| **下游供给** | → **P2**：切分标准（切分管线的依据）、要件库 JSON（护栏②的硬约束）；→ **P3**：真值 R(c)、要件库 v1（A4 的演化起点）；→ **P4**：要件解释的展示文案 |
| **验收标准** | ① 抽检 **30–50 份切分结果，泄漏扫描零命中**（验证清单第 1 项）；② 抽检 **30 条真值抽取**，确认是「法院真的在用的判断依据」而非事实复述；③ 要件库 v1 能被 P2 直接读成结构化数据 |
| **时间投入** | 全程，但**前 3 周必须交付切分标准 + 要件库 v1**（铁律 3） |
| **需补课** | 道路交通法规基础、《道路交通安全法实施条例》条文、司法文书体例（判决书固定套话） |
| **★ 关键验证** | **找懂交规的人确认「要件提炼」是否成立** —— 不成立则 A2 降级或砍掉 |

> ⚠️ **P1 的工作变了，但重要性没变、甚至更高。** 上一版 P1 写的是规则库；这一版 P1 的第一件事是**切分标准** —— 它决定数据地基建不建得起来，是 A2 的地基。

### P2 · 后端 / 架构

| 项 | 内容 |
|---|---|
| **对应 Agent** | **编排器**（LangGraph 状态图，非 Agent）、**A1 材料编目**、**A2 要件对照**（工程实现）、**护栏校验层** |
| **交付物** | ① MoMA / 大模型网关封装 ② LangGraph 状态图（4 Agent + **对抗回边** + **缺口回退边** + 轮次上限）③ **Agent 间消息 Schema**（`sender/receiver/intent/payload/confidence/evidence_ids`）④ **★ 文书数据管道** —— 解析 / **三段切分** / 脱敏 / 时间切分与去重 / 泄漏扫描 ⑤ **工具层 Function-call**（条款检索 / 要件库查询 / 文书解析 / 证据校验）⑥ **护栏校验器**（条款 ID 白名单、证据回溯、枚举校验）⑦ 评测流水线 ⑧ 思考链全量透传接口 |
| **上游依赖** | P1 的切分标准与要件库 JSON；P3 的覆盖度评测口径 |
| **下游供给** | → **P3**：`corpus/split/` 与 `corpus/truth/` 数据、稳定性基线接口；→ **P4**：消息 Schema + 思考链事件流（**不冻结则前端只能空转**） |
| **验收标准** | ① **泄漏扫描零命中 + T1/T2 去重断言通过**（验证清单第 1 项）；② 一个案件能从 A1 跑到 A4 并回到 A2（**闭环跑通一次**）；③ 连续跑 10 次，**幻觉条款 ID 出现 0 次** |
| **时间投入** | 全程；**★ 切分管线是大头，建议最先做**（原 SUMO 的 6 人天转移到这里，量级相当） |
| **需补课** | LangGraph、中文司法文书解析、向量检索 |
| **⚠️ 边界** | **Agent 不许直接拼接条款文本** —— 条款 ID 必须从法条库动态注入，见 [`JUDGMENT-DATA.md`](JUDGMENT-DATA.md) 第四节 |

### P3 · 算法 / 核心智能

| 项 | 内容 |
|---|---|
| **对应 Agent** | **★A4 复盘 Agent★★**（要件库演化）、**A3 对抗质证 Agent**、**追问规划器**（集合覆盖求解） |
| **交付物** | ① **★★ A4 要件库演化**：四级动作空间（L1 检索面 / L2 映射权重 / L3 要件项 / L4 回滚）的归因与执行逻辑 ② **A3 对抗质证策略**：矛盾类型枚举、证伪构造、不收敛判定 ③ **追问规划器**：最少问题集求解 ④ **覆盖完整度五态加权**口径实现 ⑤ **稳定性基线**（Jaccard）⑥ **三组对照实验**（单次 LLM / 多 Agent 无复盘 / 多 Agent 带闭环）⑦ 评测报告 |
| **上游依赖** | P2 的 `corpus/` 数据与护栏层；P1 的要件库 v1 与真值 |
| **下游供给** | → **P2**：A4 的动作契约（改什么、怎么落盘、怎么回滚）；→ **P4**：**要件库 v1/v2 的差异数据（这是屏幕上最值钱的那张图）** |
| **验收标准** | ① 迭代 3 轮后，覆盖完整度**确实优于第 1 轮** ② **稳定性 Jaccard ≥ 0.8**（否则「改主意」与「随机漂移」分不开）③ A4 **能回滚**自己的修改 ④ **只改要件库与参数、不改代码** |
| **时间投入** | A3 紧随切分管线之后（**它也是 Token 论证的一部分**）；A4 全程，最后两周收口 |
| **需补课** | 集合覆盖 / 贪心近似、Bandit 基础、向量检索调优 |
| **★ 这是全案的技术命门** | 闭环跑不通 → 本方向退化为通用 RAG 应用，**作品能交付但拿不到最关键那档分** |

> ⚠️ **P3 身上的担子比上一版更重**：上一版他还有视觉模块（已降为可选），现在 A3 + A4 都在他这里，而 **A4 是全案唯一的「会改主意」**。

|---|---|

| **上游依赖** | P2 的消息 Schema 与思考链事件流（**必须先冻结再开工**，铁律 2） |
| **下游供给** | → **答辩**：DEMO-SCRIPT 三个场景的全部界面；→ **P1**：演示脚本所需的界面截图 |
| **验收标准** | [`DEMO-SCRIPT.md`](DEMO-SCRIPT.md) 的三个场景能在界面上**一次走完，中途不切命令行**；**场景 3 的 v1/v2 对比能并排显示** |
| **时间投入** | 前 2 周只做线框 + 假数据；Schema 冻结后转真数据 |
| **需补课** | Streamlit/Gradio 或 Vue+FastAPI、ECharts |
| **⚠️ 最容易被挤压** | 前端看起来「不硬核」，但**演示冲击力是 RoadMind 相对另两个方向的真实优势** —— 而且这一版把「前后对比视图」做成了全场高潮，**别把它排到最后** |

## 四、★ 接口冻结表（铁律 2 的落地）

> 冻结的含义：**格式定死之后双方各自开工，改格式要两个人一起同意。**

| 接口 | 谁给谁 | 冻结点 | 内容 |
|---|---|---|---|
| **★ 三段切分 Schema** | P1 + P2 → P3 / P4 | **第 1 周末** | `case_id / year / split(T1\|T2) / source` + ① 输入段 / ②③ 真值段 |
| **证据单元 Schema** | P2 → P3 / P4 | 第 1 周末 | `evidence_id / source / content / timestamp / confidence / conflict_flag` |
| **Agent 间消息 Schema** | P2 → P4 | 第 1 周末 | `sender / receiver / intent / payload / confidence / evidence_ids` |
| **思考链事件流** | P2 → P4 | 第 1 周末 | Thought → Action → Observation → Answer 四段结构 |
| **★ 要件库 Schema** | P1 → P2 / P3 | **第 2 周末** | `clause_id / 要件清单 / 版本号 / 变更历史`（**必须可回滚**） |
| **覆盖度评测口径** | P3 → P2 / P4 | 第 2 周末 | 五态加权定义 + 稳定性 Jaccard 算法 |
| **A4 动作契约** | P3 → P2 | 第 3 周末 | 四级动作（L1–L4）的落盘格式与回滚触发条件 |

> ⚠️ **前两项是本次新增的关键接口。** 上一版这里是 `decide()` 契约与仿真状态串 —— 现在换成了**三段切分 Schema** 与**要件库 Schema**。它们各自对应一个命门（数据命门 / 技术命门）。

| 阶段 | 周次 | 目标 | P1 | P2 | P3 | P4 |

## 六、⚠️ 分工的三个风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **P3 是单点瓶颈** | A3 对抗 + A4 复盘 + 评测压在一个人身上，而 **A4 是全案唯一的「会改主意」** | A3 先行、A4 穿插；**若时间不够，砍 A3 保 A4** —— 但要记住砍 A3 会同时削弱 Token 论证 |
| **P2 ↔ P3 强耦合** | **三段切分 Schema 与要件库 Schema** 不清会导致两人互相等 | 第 2 周末必须冻结；**冻结前 P3 用桩数据**，不许等待 |
| **P1 的切分标准拖到最后** | 切分标准是 A2 的地基，也是整条数据管线的依据 | 前 3 周硬性交付，**后续只增补不重做** |
| **★ 数据拿不到** | 公开数据集不覆盖交通事故子集 | 立即降级到**手工构造 50 例**（一天可完成），**不要卡在这里等** |

## 七、三条铁律

1. **P2 与 P3 最先动工** —— **三段切分管线**（数据命门）与 **A4 闭环**（技术命门）是同一件事的两端，也都是硬阻塞项
2. **接口先冻结再各自开工** —— 前两项（三段切分 Schema / 要件库 Schema）最关键，见第四节
3. **P1 的切分标准与要件库 v1 前 3 周必须交付** —— 它们是 A2 的地基与护栏①的硬约束
