## 一、谁做什么

| 谁 | 负责 | 一句话 |
|---|---|---|
| **P1** | **数据与案例** | 把案卷材料变成能用的数据和真值 |
| **P2** | **后端 + 接入 MoMA 多个模型** | 让模型跑起来、让 Agent 串起来 |
| **P3** | **算法分析** | **A4 闭环（命门）** + A2 对照逻辑 |
| **P4** | **前端** | 让「它改主意了」在屏幕上被看见 |

**干活怎么对应到系统上**：

```
案卷材料 ─► [A1 编目] ─► 证据 ─► [A2 对照] ─► 对照表 ─► [A3 自查] ─► 最终表
                                     ▲                                  │
                                要件库（会自己改）                        │
                                     │                                  ▼
                                     └──── [A4 复盘] ◄──── 已结案件（办结文书）

P1 找数据、定切分、出要件库        P2 接 MoMA 模型 + 把上面这条串起来
P3 写 A2 的对照逻辑 + A3 自查 + ★A4  P4 把结果显示出来
```

> **这套分工对比赛有利**：MoMA 是本次比赛指定的平台。P2 的活（**接平台的多个模型**）本身就是评分点，不是纯内部工程。

## 四、P2 的第一件事不是写代码，是「摸清 MoMA 上有什么模型」

> **这是本次新增的外部依赖，也是全案的第二个硬阻塞（第一个是 P1 的组委会邮件）。**
> **Day 1 就要做，因为模型列表会反过来决定技术选型。**

### P2 在 D1 要问清楚这 5 件事

1. 账号和额度：能不能拿到？Token 配额多少？
2. **有哪些模型**：文本 / 多模态 / 向量（embedding）分别有哪些？
3. **能不能稳定输出 JSON**？—— 这是护栏和 A2 对照表的前提，不能结构化输出后面全塌
4. **上下文有多长**？—— 一份判决书可能几千字，A4 要一次塞多份案件
5. 有没有现成的编排 / Agent 能力可以少写点代码？

### 摸完之后要产出一张「环节 → 模型」选型表

| 环节 | 需要什么能力 | 怎么选 |
|---|---|---|
| **A1 材料编目** | 长文本抽取 → JSON | 上下文要长；输出要能稳定成 JSON |
| **A2 要件对照** | 推理 + 结构化输出 | 推理能力最强的那个 |
| **A3 自查** | 找矛盾 | **故意换一个模型** —— 见下 |
| **A4 复盘归因** | 跨案件归纳 | 上下文最长（一次要塞多份案件） |
| 法条检索 | embedding | 中文语料表现好的 |

> **★ 一个不花钱的巧劲**：**A2 和 A3 用不同的模型。**
> 不同模型的偏差不一样，让它俩互挑毛病比用同一个模型"自己审自己"更真实 —— 这正好强化了「目标函数对抗」的论证，而且是**平台多模型能力的直接体现**。
