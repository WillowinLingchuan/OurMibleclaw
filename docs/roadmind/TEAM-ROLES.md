## 一、口径说明（先对齐这个，再往下看）

> ⚠️ **本仓库统一采用一套 P 编号映射**，三个候选方向共用。见 [`../../README.md`](../../README.md)，BoostForge 与 PathPilot 同此口径。

| 编号 | 角色 |
|---|---|
| **P1** | 产品 + 业务 |
| **P2** | 后端 / 架构 |
| **P3** | 算法 / 核心智能 |
| **P4** | 前端 / 全栈 |

**为什么必须统一**：早先 RoadMind 的两份文档用过两套编号 —— `EXECUTION-PLAN.md` 第七节曾写「P1 调度 / P2 视觉 / P3 前端 / P4 业务」，而 `SUMO-INTEGRATION.md` 第十节写的是「P1 队长 / P2 后端 / P3 算法 / P4 业务」。**同一个「P3」，一份文档里是前端、另一份里是算法。**（两处均已按本文件统一。）

统一之后的好处是：**换方向不换人**。最终选 BoostForge 还是 RoadMind，四个人的角色含义始终一致，不需要重排座次。

## 二、角色分工总表

| 角色 | 一句话定位 | 负责的 Agent / 模块 | 核心交付物 |
|---|---|---|---|
| **P1 · 队长 / 产品 + 交通业务** | 定义「什么算紧急」 | 业务规则层（为 ②④⑤ 供知识底座） | 交规规则库、气象-交通风险映射表、分级标准、设计报告、答辩 PPT |
| **P2 · 后端 / 架构** | 让 7 个 Agent 能互相说话，也能和 SUMO 说话 | 总调度、①③⑤⑥ 的工程实现、工具层、SUMO 接入 | 编排层、消息 Schema、6 个 Function-call、TraCI 适配层、闭环脚本 |
| **P3 · 算法 / 核心智能** | 全案唯一「会改主意」的地方 | ①视觉识别、**★⑦复盘**、⑥权重推演 | 复盘 Agent、对照组实验、评测报告、YOLOv8 验证结果 |
| **P4 · 前端 / 全栈** | 让「会改主意」在屏幕上被看见 | 交互层（不写 Agent，消费全部输出） | 治理端大屏、公众端出行页、**思考链可视化**、上架材料 |

## 三、逐人详表

### P1 · 队长 / 产品 + 交通业务

| 项 | 内容 |
|---|---|
| **对应 Agent** | 为 **②分级 / ④研判 / ⑤预警** 提供知识底座（写规则，不写 Agent 代码） |
| **交付物** | ① **交规规则库 v1**（≥30 条高频条款，含**要件拆解**）② 气象-交通风险映射表（结构化）③ 故障分级标准表 ④ 方案设计报告 ⑤ 答辩 PPT + 主讲 + 彩排 |
| **上游依赖** | 无（本方向的知识底座是**根节点**，不等人） |
| **下游供给** | → **P2**：规则库以 JSON 形式硬约束 LLM 输出（幻觉抑制防线②）；→ **P3**：分级阈值初值、气象-风险映射表；→ **P4**：规则解释的展示文案 |
| **验收标准** | 拿 5 个真实事故案例走一遍，规则库能覆盖其中 **≥4 个**；映射表能被 P3 直接读成结构化数据 |
| **时间投入** | 全程，但**前 3 周必须交付 v1**（铁律 3） |
| **需补课** | 道路交通法规基础、气象对路面附着系数的影响常识 |
| **★ 关键验证** | 验证清单第 3 项：**找懂交规的人确认「要件提炼」是否成立** —— 不成立则研判 Agent 降级或砍掉 |

---

### P2 · 后端 / 架构

| 项 | 内容 |
|---|---|
| **对应 Agent** | **总调度 Agent**（自主决策点：并发事件优先级仲裁）、**①感知**（接入部分）、**③疏导**、**⑤预警**、**⑥出行**（工程部分）；**TraCI 决策适配层** |
| **交付物** | ① MoMA / 大模型网关封装 ② LangGraph 状态图（7 Agent + 循环边 + 仲裁边）③ **Agent 间消息 Schema**（`sender/receiver/intent/payload/confidence`）④ **工具层 6 个 Function-call**（天气 / 路况 / 交规检索 / 路网拓扑 / SUMO 接口 / 工单派发）⑤ SUMO 接入全套：安装、路网车流、TraCI 生命周期、**决策适配层**、闭环脚本 ⑥ 思考链全量透传接口 |
| **上游依赖** | P1 的规则库（工具层「交规检索」的数据源）；P3 的 `decide()` 函数契约 |
| **下游供给** | → **P3**：仿真状态串 + 可调用的仿真接口；→ **P4**：消息 Schema + 思考链事件流（**不冻结则前端只能空转**） |
| **验收标准** | 单事件能从①一直跑到⑦并回到②（**闭环跑通一次**）；7 个 Agent 的消息可被前端完整回放 |
| **时间投入** | 全程；**SUMO 部分是大头，建议最先做**（验证清单第 1 项 = 硬阻塞） |
| **需补课** | LangGraph、TraCI API |
| **⚠️ 边界** | 决策适配层必须强制 **Agent 不许直接写 TraCI** —— 见 [`SUMO-INTEGRATION.md`](SUMO-INTEGRATION.md) 第四节 |

### P3 · 算法 / 核心智能

| 项 | 内容 |
|---|---|
| **对应 Agent** | **①感知 Agent**（YOLOv8 识别部分）、**★★⑦复盘 Agent★**、**⑥出行 Agent**（风险→代价权重推演） |
| **交付物** | ① **YOLOv8 在 UA-DETRAC 上的车辆/占道识别结果**（验证清单第 2 项）② **★复盘 Agent**：三个回流源的偏差诊断与参数修正（②③⑤）③ SUMO 闭环里的 `agent.decide()` —— 把 `history` 变成 `next_rule` ④ **三组对照实验**（纯规则 / 无回流 / 带回流）⑤ 评测报告 |
| **上游依赖** | P2 的仿真状态串与接口；P1 的分级标准与风险映射表 |
| **下游供给** | → **P2**：`decide()` 的返回值契约；→ **P1**：修正后的阈值（写回规则库说明）；→ **P4**：修正前后的对比数据（**这是大屏上最值钱的那张图**） |
| **验收标准** | 迭代 N 轮后，分级与疏导指标**确实优于第 1 轮**（`EXECUTION-PLAN.md` 第八节「★学习效果」核心指标）；**只改参数、不改代码** |
| **时间投入** | 视觉部分**限时 1 周**出结果；复盘闭环紧随 SUMO 之后 |
| **需补课** | YOLOv8、参数搜索 / Bandit 基础 |
| **★ 这是全案的技术命门** | 复盘闭环跑不通 → 本方向退化为普通调度系统 |

### P4 · 前端 / 全栈

| 项 | 内容 |
|---|---|
| **对应 Agent** | 不写 Agent，**消费全部 Agent 的输出**（对应 [`ARCHITECTURE.md`](ARCHITECTURE.md) 的交互层） |
| **交付物** | ① 治理端大屏（Folium 地图：事故点 / 风险点 / 分流路径）② 公众端出行页（**三套方案并列** + 全程分级预警）③ **Agent 思考链可视化**（Thought→Action→Observation 逐条回放，**比赛加分项，务必做**）④ **复盘前后规则对比视图** ⑤ ECharts 指标曲线 ⑥ AI Store 上架材料 |
| **上游依赖** | P2 的消息 Schema 与思考链事件流（**必须先冻结再开工**，铁律 2） |
| **下游供给** | → **答辩**：DEMO-SCRIPT 三个场景的全部界面；→ **P1**：演示脚本所需的界面截图 |
| **验收标准** | [`DEMO-SCRIPT.md`](DEMO-SCRIPT.md) 的三个场景能在界面上**一次走完，中途不切命令行** |
| **时间投入** | 前 2 周只做线框 + 假数据；Schema 冻结后转真数据 |
| **需补课** | Streamlit/Gradio 或 Vue+FastAPI、Folium、ECharts |
| **⚠️ 最容易被挤压** | 前端看起来「不硬核」，但**演示冲击力是 RoadMind 相对另两个方向的真实优势** —— 别把它排到最后 |

## 四、★ 接口冻结表（铁律 2 的落地）

> 冻结的含义：**格式定死之后双方各自开工，改格式要两个人一起同意。**

| 接口 | 谁给谁 | 冻结点 | 内容 |
|---|---|---|---|
| **Agent 间消息 Schema** | P2 → P4 | 第 1 周末 | `sender / receiver / intent / payload / confidence` |
| **思考链事件流** | P2 → P4 | 第 1 周末 | Thought → Action → Observation → Answer 四段结构 |
| **仿真状态串** | P2 → P3 | 与 SUMO 同批 | 见 [`SUMO-INTEGRATION.md`](SUMO-INTEGRATION.md) 4.3 节字段定义 |
| **`decide()` 契约** | P3 → P2 | 与 SUMO 同批 | 入参 `history` / 出参 `next_rule` |
| **交规规则库 JSON Schema** | P1 → P2 / P3 | 第 2 周末 | 条款 / 要件 / 适用条件 |

## 五、阶段划分（10 周标准档）

| 阶段 | 周次 | 目标 | P1 | P2 | P3 | P4 |
|---|---|---|---|---|---|---|
| **① 验证** | W1 | 回答「是不是智能体」 | 规则库启动；**发组委会邮件** | **SUMO 最小闭环**（验证清单 1） | **YOLOv8 跑通 UA-DETRAC**（验证清单 2） | 线框 + 假数据 |
| **② 骨架** | W2–W3 | **接口冻结** | **规则库 v1 交付**；分级标准 | 编排骨架 + 消息 Schema 冻结 | 复盘 Agent 设计 + `decide()` 契约 | 思考链组件（吃假数据） |
| **③ 打通** | W4–W6 | 闭环跑通 | 气象映射表；**30 条条款找人验证** | 7 Agent 全链路 + 工具层 | 三个回流源接入 | 大屏 + 出行页接真数据 |
| **④ 加固** | W7–W8 | 用数据说话 | 方案设计报告 | 稳定性 / 并发事件仲裁 | **三组对照实验 + 评测报告** | 复盘前后对比视图 |
| **⑤ 交付** | W9–W10 | 答辩 | PPT + 主讲 + 彩排 | 上架技术支持 | 数字复核 | AI Store 材料 |

> 验证清单原文见 [`EXECUTION-PLAN.md`](EXECUTION-PLAN.md) 第十一节。

## 六、⚠️ 分工的三个风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **P3 是单点瓶颈** | 视觉 + 复盘闭环 + 评测压在一个人身上，而**复盘又是命门** | 视觉部分**限时 1 周**，跑不通就走「公开数据集离线验证」退路，**把时间让给复盘** |
| **P2 ↔ P3 强耦合** | `decide()` 契约不清会导致两人互相等 | 第 2 周末必须冻结契约；**冻结前 P3 用桩函数**，不许等待 |
| **P1 的规则库拖到最后** | 规则库是幻觉抑制的底座，也是 ④研判 的唯一依据 | 前 3 周硬性交付 v1，**后续只增补不重做** |

---

## 七、三条铁律

1. **P2 与 P3 最先动工** —— SUMO 最小闭环与复盘闭环是同一件事的两端，也是技术命门
2. **接口先冻结再各自开工** —— P2↔P4 的消息 Schema、P2↔P3 的 `decide()` 契约，见第四节
3. **P1 的规则库是幻觉抑制的底座，前 3 周必须交付 v1**
