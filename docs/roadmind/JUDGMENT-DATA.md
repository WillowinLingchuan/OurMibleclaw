## 二、★ 判决书三段结构化切分（约 1.5 人天 + 1 人天抽检）

> **本章是全案命门。** 做砸了，后面全部白做。

### 2.1 要切成什么样

```
一份判决书
 ├─ ① 事实材料段（当事人诉称 + 经审理查明的事实） → 【输入材料】
 ├─ ② 交警认定段（"交警部门认定……"）            → 【真值】，必须从输入中剥离
 └─ ③ 法院说理段（"本院认为……"）                → 【真值】，必须从输入中剥离
```

落盘为三份纯文本 + 一份元数据：

```
corpus/split/
├── 0001.case.txt      ← ① 只喂给系统
├── 0001.truth.txt     ← ② + ③ 拼起来，只给评测用
└── 0001.meta.json     ← {case_id, year, court, source, split: "T1"/"T2"}
```

### 2.2 切分标记（中文判决书的固定套话）

| 段 | 起 | 止 |
|---|---|---|
| **① 事实材料段** | `当事人……诉称` / `经审理查明` / `本院经审理认定事实如下` | `上述事实，有下列证据证明` / `以上事实，有……为证` |
| **② 交警认定段** | `交警部门认定` / `公安机关交通管理部门认定` / `经交警部门认定` | 下一个句号（**通常只有一句话**） |
| **③ 法院说理段** | `本院认为` | `依照《……》第……条之规定，判决如下` |

### 2.3 ⚠️ 最容易踩的坑：② 物理上嵌在 ① 里

判决书的真实形态常常是：

```
经审理查明：……（事故经过）……。交警部门认定，张某负事故全部责任。……
```

**② 就嵌在 ① 的段落中间。** 如果只是按「本院认为」一刀切，② 会**留在输入材料里**，等于把答案直接喂给了系统。

**切分后必须做的自检**：

```python
# 对每一份 ① 段做泄漏扫描 —— 有任何一条命中，这份文书就要人工复核
LEAK_PATTERNS = [
    "交警部门认定", "交警认定", "公安机关交通管理部门认定",
    "负全部责任", "负主要责任", "负次要责任", "负同等责任", "无责任",
]
```

> **规矩：① 段里不得出现任何责任认定性质的表述。** 出现了，说明这一段没切干净。

### 2.4 脱敏（做进管道，不是可选项）

| 字段 | 处理 |
|---|---|
| 当事人姓名 | → 占位符 `甲 / 乙 / 丙` |
| 身份证号、车牌号、住址、电话 | → 掩码 `[已脱敏]` |
| 保险公司名 | 保留（不影响要件判断） |

> **在报告里展示「脱敏前后样例」——这是加分项，不是负担。**

### 2.5 时间切分（T1 构建期 / T2 留出期）

| 集合 | 用途 | 划分 |
|---|---|---|
| **T1** | 构建要件库 v1、提取条款与要件 | 早期年份 |
| **T2** | **只用于评测与复盘**，不参与知识构建 | 后期年份 |

**两条纪律（都必须在脚本里断言）**：

1. **按案件去重再切分** —— 同一起事故可能有**一审 + 二审**两份文书。若一审进 T1、二审进 T2，**就是同一个案子左右手互搏**，指标必然虚高。**去重键：当事人 + 事故时间 + 事故地点。**
2. **T2 内部再留一件 D 出来** —— 演示用（见第五章）。**D 不参与 A4 的复盘，只做「同题重做」的题面。**

```python

assert demo_case_id not in a4_review_case_ids, "演示案件 D 不能进入复盘集"
```

## 三、要件真值怎么构造（约 1 人天）

### 3.1 真值是什么

对案件 c，真值要件集 **R(c)** = 从 ②③ 段中抽取的、**交警与法院实际援引的判断依据**。

> 注意：抽的是**依据**，不是**结论**。我们不关心「判谁全责」，只关心「他们是靠哪几条要件判的」。

### 3.2 抽取三步

| 步 | 抽什么 | 方法 |
|---|---|---|
| 1 | **援引条款** | 正则 `《[^》]+》第[一二三四五六七八九十百零]+条` |
| 2 | **要件短语** | 从「本院认为」句内抽判断依据短语：`未保持安全距离` / `未让右方来车先行` / `违反信号灯指示` / `未按规定车道行驶` / `超速` … |
| 3 | **人工校验** | **P1 抽检 30 条**，确认要件短语是「法院真的在用的判断依据」，而不是复述事实 |

> ⚠️ 第 3 步不能省。自动抽出来的短语里会混进**事实陈述**（「张某驾驶小客车」）而不是**判断依据**（「张某未保持安全距离」）。这个区分就是 P1 的业务判断，是 A2 的地基。

### 3.3 输出格式

```json
{
  "case_id": "0001",
  "year": 2018,
  "split": "T1",
  "clauses": ["《道路交通安全法实施条例》第91条"],
  "requirements": [
    "后车未与前车保持安全距离",
    "前车无正当理由急刹"
  ],
  "disputed": ["前车是否急刹"]
}
```

> `disputed` = 法院**明确当成争议焦点在讲**的要件。它是「争议点命中率」这个指标的分母，**必须单独标出来**，不能混在 `requirements` 里。

### 3.4 验收

- [ ] `corpus/truth/T1.jsonl` 与 `T2.jsonl`，每案一条
- [ ] P1 已完成 30 条抽检，抽检结论有记录
- [ ] `disputed` 字段在 T2 上有覆盖（否则争议点命中率算不出来）

## 四、★ 护栏：LLM 只做推理编排，不做事实与法条生成

> 本章原则**直接从原 SUMO 接入方案平移**（「LLM 只输出结构化决策 JSON，由一层确定的适配器翻译」）——原则跨方向成立，只是翻译目标从仿真指令换成了结构化输出。

### 4.1 原则

**大模型只做两件事：判断、整理。** 所有事实与法条一律走工具层与白名单。

### 4.2 四条硬护栏

| # | 护栏 | 怎么实施 |
|---|---|---|
| **1** | **条款 ID 必须从法条库动态注入** | 检索命中后把条款原文塞进 prompt，要求 LLM **只返回 `clause_id`**；返回库里没有的 ID → 直接判为幻觉，重做 |
| **2** | **证据 ID 必须回溯到案卷** | A2 每条结论必须带 `evidence_ids`，校验器逐个核对是否存在于 A1 的证据单元集；不存在 → 重做 |
| **3** | **枚举白名单** | 状态只能取 `具备 / 待确认 / 缺失`；超出即报错 |
| **4** | **免责声明不可关** | 每份输出强制带固定尾注，**前端不可关闭**（产品级合规，不能只靠嘴说） |

### 4.3 ★ 条款 ID 必须动态注入，不能写死

与「路口 ID 必须动态注入」同一个道理：**写死的条款 ID 会在法条修订或案件类型变化时静默失效，而且失败得毫无声响。**

```python
# ❌ 不要这样
prompt = "请判断是否符合《道路交通安全法实施条例》第91条"

# ✅ 这样
hits = clause_index.search(case_facts, top_k=20)      # 检索面由 A4 的 L1 动作调整
prompt = (
    "以下是候选条款原文，你只能从中选择，不得引用未列出的条款：\n"
    + "\n".join(f"[{h.id}] {h.text}" for h in hits)
)
```

> **检索面 `top_k` 就是 A4 的 L1 动作对象。** 上一轮召回 30 条，复盘发现法院援引的条款里有 8 条不在其中 → A4 把检索面扩到 38 条。**这才是「改自己的输入空间」，不是调排序。**

### 4.4 验收

- [ ] 对同一条结论连续跑 10 次，**幻觉条款 ID 出现 0 次**
- [ ] 免责声明出现在输出 schema 里，且前端无法隐藏

## 五、★ 回流指标怎么取（约 0.5 人天）

### 5.1 覆盖完整度怎么算

对案件 c：系统声明要件集 **S(c)**，真值要件集 **R(c)**。

**不是简单 F1 —— 五态加权：**

| 状态 | 计分 | 理由 |
|---|---|---|
| 标「具备」且真值具备 | 1.0 | 正确 |
| 标「待确认」且真值确为争议点 | 1.0 | **正确且诚实，满分** |
| 标「待确认」但真值无争议 | 0.5 | 过度谨慎，扣分但远轻于漏 |
| 标「具备」但真值不成立 | 0.3 | 与真值冲突 |
| **完全没提（缺失）** | **0** | **最严重的失败模式** |

> ★ **为什么权重偏向 recall**：**漏一条要件 = 交警少看一条材料；多给一条 = 交警多扫一眼。** 代价不对称。这个理由必须写进报告 —— 它是「为什么不是简单 F1」的答案。

### 5.2 四个指标一起取

| 指标 | 算法 | 看什么 |
|---|---|---|
| **要件覆盖完整度** | Σ五态得分 / \|R(c)\| | ★ 主指标 —— **它上升 = 闭环有效** |
| **要件缺失率** | 系统完全没提的真值要件数 / \|R\| | 最严重的失败模式，必须单列 |
| **争议点命中率** | S 中标「待确认」项 ∩ R.disputed / \|R.disputed\| | ★ **衡量判断力而非查表能力的硬指标** |
| 条款召回率 | R.clauses ∈ 系统候选集 的比例 | 直接度量 A4 的 L1 动作效果 |

### 5.3 稳定性基线（不算这个，「改主意」就无从谈起）

**同一版本、同一案件重复运行 N 次（建议 N=5），要件集的 Jaccard 相似度必须高。**

> **没有稳定性，就没有「改主意」，只有「乱改」。** 这一条是答辩现场挡「随机漂移」质疑的唯一挡箭牌。

### 5.4 输出：喂回给 A4 的凭证

```json
{
  "round": 2,
  "clause_version": "v2",
  "requirement_set_version": "req-v2",
  "coverage": 0.71,
  "coverage_delta_vs_last_round": 0.09,
  "missing_rate": 0.08,
  "dispute_hit_rate": 0.62,
  "stability_jaccard": 0.88,
  "rolled_back": false
}
```

> **`coverage_delta_vs_last_round` 就是「闭环存在」的证明。** 有了它，A4 才可能改主意。
> **`stability_jaccard` 是它的守门人** —— 分数涨了但 Jaccard 崩了，那不是学好了，是开始乱答。

## 六、★ 最小闭环脚本（约 1 人天，可直接改成真代码）

### 6.1 闭环长什么样

```
要件库 v1 ──→ 在 T2 上评测 ──→ 覆盖完整度 = 0.62
                  │
                  ▼
        A4 读 T2 中「除 D 以外」的已结案件，归因
                  │
                  ▼
        要件库 v2（新增 3 项 / 降权 1 项）
                  │
                  ▼
        ★ 把案件 D 同题重做 ──→ 覆盖完整度 = 0.71  ✅ 上升
                  │
                  └── 若下降 → A4 回滚，返回 v1
```

### 6.2 骨架

```python
"""run_loop.py —— 最小闭环。先跑通管道，再换真 Agent。"""
import json, random
from pathlib import Path

SEED = 42
random.seed(SEED)          # ★ 固定种子 = 可复现
T2 = json.loads(Path("corpus/truth/T2.jsonl").read_text(encoding="utf-8").splitlines()[0]) if False else None

def load_jsonl(p):
    return [json.loads(l) for l in Path(p).read_text(encoding="utf-8").splitlines() if l.strip()]

def evaluate(req_library, cases):
    """在一批案件上算覆盖完整度。真实现里这里是 A2 的输出对 R(c)。"""
    scores = []
    for c in cases:
        declared = a2_apply(req_library, c)          # ← Agent 在这里
        scores.append(coverage(declared, c["requirements"], c["disputed"]))
    return sum(scores) / len(scores)

def a2_apply(req_library, case):
    """★★ 这里换成你的 A2 要件对照 Agent ★★"""
    # 占位实现：要件库有什么就报什么，够跑通管道
    return {r: "待确认" for r in req_library}

def coverage(declared, truth, disputed):
    """五态加权 —— 见第五章 5.1"""
    total = 0.0
    for r in truth:
        if r not in declared:                    total += 0.0   # 缺失，最严重
        elif declared[r] == "具备":               total += 1.0
        elif declared[r] == "待确认" and r in disputed: total += 1.0
        elif declared[r] == "待确认":             total += 0.5
        else:                                    total += 0.3
    return total / max(len(truth), 1)

def run_round(req_library, review_cases, eval_cases):
    """一轮：A4 读复盘集 → 改要件库"""
    new_lib = req_library.copy()

    # ★★ 这里换成你的 A4 复盘 Agent ★★
    #    占位实现：复盘集里出现、而我们库里没有的要件，加进去
    known = set(req_library)
    for c in review_cases:
        for r in c["requirements"]:
            if r not in known:
                new_lib[r] = "新增"          # ← L3 动作：改自己的行为集合

    return new_lib

# ================= 闭环 =================
t1_cases   = load_jsonl("corpus/truth/T1.jsonl")
t2_cases   = load_jsonl("corpus/truth/T2.jsonl")

demo_id    = t2_cases[0]["case_id"]                 # ← 演示用案件 D
review     = [c for c in t2_cases if c["case_id"] != demo_id]   # ★ D ∉ 复盘集
demo_case  = [c for c in t2_cases if c["case_id"] == demo_id]

req_lib = sorted({r for c in t1_cases for r in c["requirements"]})   # 要件库 v1

history = []
for r in range(1, 4):
    cov = evaluate(req_lib, demo_case)              # ★ 每轮都在同一个 D 上评测
    history.append({"round": r, "library_size": len(req_lib), "coverage": round(cov, 3)})
    print(f"round {r}: 要件 {len(req_lib)} 项，D 的覆盖完整度 {cov:.3f}")

    if r < 3:
        req_lib = run_round(req_lib, review, demo_case)

Path("loop_history.json").write_text(
    json.dumps(history, ensure_ascii=False, indent=2), encoding="utf-8")

if len({h["coverage"] for h in history}) == 1:
    print("⚠️ 覆盖完整度没变化 —— 闭环没起作用，检查 A4")
```

### 6.3 ★ 先用「假 Agent」把管道跑通，再换成真 LLM

上面那段写死的 `a2_apply` / `run_round` **不是偷懒，是必要的调试顺序**。

理由：管道错（切分错、真值错、去重错）和 Agent 差，症状都是「指标不动」。**先用假 Agent 确认管道能跑出变化，再接真 LLM** —— 否则你会花三天调 prompt，而问题在切分。

### 6.4 验收

- [ ] `run_round` 跑 3 轮，`coverage` **有变化**（哪怕变差也算打通）
- [ ] `stability_jaccard` ≥ 0.8（同版本重复跑）
- [ ] `loop_history.json` 落盘
- [ ] **把 `a2_apply` 换成真 Agent 后，结论不变**

## 八、坑与对策

| 坑 | 后果 | 对策 |
|---|---|---|
| **★ 交警认定段嵌在事实段里没剥出来** | **标签泄漏，所有指标虚高** | 2.3 的泄漏扫描 + 人工抽检，**这是第 1 号杀手** |
| **★ 一审/二审文书分到 T1/T2** | 同一案件左右手互搏 | 按「当事人+事故时间+地点」去重后再切分，脚本里断言 |
| 判决书格式年份差异大，正则失配 | 切分成功率低 | 抽样 20 份先定标记表；失配的走人工，不要硬正则 |
| 自动抽的要件短语混进事实陈述 | 真值不干净，指标无意义 | P1 抽检 30 条（3.2 第 3 步），**不能省** |
| 法条有修订，早年语料引的条款已变 | 条款召回率算不准 | 只用**要件层面稳定**的条款（安全距离、让行规则）；报告写明时间边界 |
| 文书里当事人的口语化陈述含方言/错别字 | 解析出错 | 脱敏阶段一并做繁简与常见错字归一 |
| 覆盖完整度涨了但 Jaccard 崩了 | 不是学会，是乱答 | 5.3 稳定性基线必须与主指标同时看 |
| 把 `disputed` 混进 `requirements` | 争议点命中率算不出来 | 3.3 输出格式里两字段分开 |

## 九、退路

| 情况 | 降级方案 | 代价 |
|---|---|---|
| 公开数据集都拿不到 | **P1 手工构造 50 例要件真值**（一级退路 ③） | 规模小，但闭环照样能演示「同题重做」 |
| 三段切分做不干净 | 只保留**格式规范、套话完整**的子集（可能只剩 20–30 份） | 数据变少，但指标可信 |
| 要件库演化跑不通 | 退化为「要件对照工具 + 手工模板」，A1–A3 仍然完整 | **作品成立**，拿不到最关键那档分 |
| 时间严重不足 | 砍掉对抗质证 A3，保留 A1/A2/A4 | ⚠️ **Token 论证同时被砍**，见方案第三节代价三 |

> ⚠️ 上述降级**都不致命** —— 符合团队决策标准：**硬核部分是可选的，不是承重的。**
> ⚠️ 但要注意：**闭环在技术上是可选的，在叙事上是承重的** —— 降级后作品能交付，但很难赢。
